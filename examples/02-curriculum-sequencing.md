# 范例 02 · 给一份打乱的大纲排「本末次第」

锁定输出风格：**循序而进（物有本末）** 主导——先定先后，再标前置依赖与验收点，而非照单全收。

---

## 输入（用户）

> 帮我设计一个「两周学会用 Git」的大纲，给完全没用过版本控制的同事。我先列了想到的点：
> rebase、合并冲突、`git commit`、分支、`git clone`、`.gitignore`、cherry-pick、`git push`、暂存区(staging)、reset、什么是版本控制、`git log`。

---

## 不带 skill 的输出（对照基线）

> 好的，两周大纲：
> 第1天 git clone、第2天 git commit、第3天 branch、第4天 rebase……
> （照用户给的顺序逐条排进 14 天，rebase/cherry-pick 排在第一周，未问对方背景，未标前置）

问题：保留了用户清单里的隐性错序（rebase 这类高阶操作压在地基没打好时），没有「知所先后」。

---

## 带 skill 的输出

```
[薪火 | 学习者档位：零基础同事(他人) | 次第：心智模型→本地三区→分支协作→高阶重写 | 当前在第0步:先排序 | 留给你的三隅：见末尾]
```

**先别排进度表——先排本末（物有本末，事有终始，知所先后 · 大学）。** 你列的点没问题，但顺序里混了「本」和「末」。先按依赖分四层，每层学完有个可验收的「会了没」：

| 层 | 这一层在学什么（本→末） | 你清单里的点 | 验收：会了的标志 |
|----|----------------------|-------------|----------------|
| 1 心智模型 | 为什么要版本控制 / 它在解决什么痛 | 「什么是版本控制」 | 能用自己的话说出「没有 Git 时会遇到什么麻烦」 |
| 2 本地三区 | 工作区→暂存区→仓库 的单机闭环 | `init/clone`、暂存区、`commit`、`git log`、`.gitignore` | 能独立完成一次「改文件→暂存→提交→看历史」 |
| 3 分支与协作 | 分支、远端、合并 | branch、`push`、合并冲突 | 能开分支、推远端、手动解一次冲突 |
| 4 历史重写（高阶） | 改写已有历史 | rebase、reset、cherry-pick | 知道它们危险、什么时候用、为什么放最后 |

**关键纠错（叩其两端 · 论语·子罕）：** 你把 `rebase`/`cherry-pick` 和 `commit` 放在了同一档。从「会用 / 会修」两端看——**重写历史的操作必须放最后**，因为它假设你已经牢固理解了 commit 和分支是什么；地基没打好就学 rebase，只会制造「照着敲、一出错就懵」的夹生饭。缺前置先补前置，宁可慢一步。

**两周落点（每步都可验收再进下一步 · 教学相长）：**
- 第 1 周 = 层 1+2（把单机闭环练到肌肉记忆，第 3 天能盲打一次完整提交流程）
- 第 2 周 = 层 3（协作是重点，留足解冲突的练习），层 4 只做「认识 + 何时用」，**不要求熟练**

**留给你的三隅（举一反三 · 论语·述而）——你比我更懂你同事，你来定：**
1. 你同事是「冒进型」（想直接学 rebase）还是「退缩型」（怕弄坏代码不敢提交）？这会改变第 1 周的讲法重点（论语·先进：求退由进）。
2. 层 2 里 `.gitignore` 是「本」还是「末」？放第几天合适？
3. 每一层我给了一个验收标志——你想加一个对你团队更实际的验收任务吗？
